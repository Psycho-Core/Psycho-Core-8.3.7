 STEP 3 - THE CRITICAL GOTCHA: DISABLE THE OLD updates/ FOLDERS
===========================================================================
This is the part that will bite you if skipped, and it's the main thing
this report exists to flag.

My 3 SQL files already have every update file's content merged directly
into them (all 29 world/ updates, both characters/ updates - see Step 1).
But sql/updates/world/ and sql/updates/characters/ still physically
contain those same 31 .sql files.

If you leave them where they are, after the updater loads your new
psycho_*.sql base files, it will ALSO try to apply every file still
sitting in sql/updates/world/ and sql/updates/characters/ - because the
updater decides what to apply by checking a tracking table (normally
called `updates`), not by checking whether the content is already
there. Since this is a fresh import via my consolidated files, that
tracking table will be empty, so the updater will think none of those
31 updates have ever been applied and will try to run all of them again
- on data that already has them baked in. Expect duplicate-key errors,
possibly a halted startup.

PICK ONE of these two fixes:

  Option A (simplest - recommended):
    Move sql/updates/world/*.sql and sql/updates/characters/*.sql out
    of those folders entirely (e.g. into an "already_applied/" folder
    outside sql/, or just delete them if you keep a copy elsewhere).
    With nothing left in updates/world/ and updates/characters/, the
    updater has nothing further to apply after loading your base files
    - exactly the "look and load only them and be happy" behavior you
    asked for.

  Option B (if you want to keep the files in place for reference):
    Manually pre-populate the `updates` table in psycho_characters and
    psycho_world with one row per already-applied filename before first
    startup, so the updater's own bookkeeping considers them done and
    skips re-applying. Update Step 2 - the actual table name/columns
    are visible at the same dump location).
    This is more fragile - the matching is also done with a CRC32-style
    file hash, not just the filename. Find UpdateFetcher.cpp's hash
    logic if you want to do this correctly. Otherwise Option A is far
    less likely to slip mid-update.

sql/updates/hotfixes/ (the single fishing-spell patch) can stay as-is
either way - it's a separate concern from the base-file question and
isn't pre-merged into anything yet, since there's no hotfixes base to
merge it into.
