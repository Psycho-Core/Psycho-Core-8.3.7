  PurgeAllBots() left rows in ai_playerbot_db_store,

WHAT WAS IN THE TWO ZIPS:

[NOTE] DB-3.zip was NOT used and should NOT be imported.
  Reason: it opens with `DROP DATABASE IF EXISTS` + recreate, and its
  245 tables hold the exact same row counts as DB-4's world.sql — it's
  simply an older/differently-formatted export of the same data, with no
  unique content. Importing it would be pure data loss risk for no gain.

[FIXED] Database name mismatches — all 3 base files plus all 31 update
  files referenced the core's original example DB names (auth_bfa,
  characters_bfa, world_bfa) instead of your actual names. Every
  CREATE DATABASE, USE, and 2 hardcoded inline references
  (`world_bfa`.`trainer_spell` in 2022_01_24_world_fix_trainers.sql)
  were rewritten to psycho_auth / psycho_characters / psycho_world.

[FIXED] MariaDB 11.8.6 strict-mode zero-date rejection — 1_auth.sql has
  legacy TIMESTAMP columns defaulting to '0000-00-00 00:00:00'; world.sql
  has 15 similar zero-date values. MariaDB 11.x's default strict sql_mode
  includes NO_ZERO_DATE/NO_ZERO_IN_DATE, which would reject these inserts
  outright. Fixed by wrapping each file's import with:
    SET SESSION sql_mode = REPLACE(REPLACE(@@SESSION.sql_mode,
      'NO_ZERO_DATE',''), 'NO_ZERO_IN_DATE','');
  ... and restoring the original sql_mode at the end of the file.
  (characters.sql had zero zero-dates — no fix needed there.)

[FIXED] CRLF line endings — DB-4's 1_auth.sql and 2_characters.sql used
  Windows CRLF throughout; normalized to LF for clean MariaDB import.

[FIXED] Update-file application order — confirmed by reading
  src/server/database/Updater/UpdateFetcher.h directly: the core's own
  DBUpdater enumerates update files into a std::set<...,PathCompare>,
  i.e. plain lexicographic filename sort (same as `ls | sort`). All 29
  world/, 2 characters/, and 1 hotfixes/ update files were concatenated
  onto their respective base files in that exact order, so the
  consolidated files behave identically to what your worldserver's own
  auto-updater would have produced.

[FIXED] mod-psychobot SQL folded in — appended to the matching
  consolidated file in deterministic (alphabetical) order:
    auth:       psychobot_rbac.sql
    characters: psychobot_custom_strategy.sql, psychobot_db_store.sql,
                psychobot_random_bots.sql, psychobot_strategies.sql
    world:      psychobot_cache.sql, psychobot_indexes.sql,
                psychobot_names.sql, psychobot_rpg_races.sql,
                psychobot_texts.sql

[NOTE — GAP, NOT FIXED] No base schema for psycho_hotfixes anywhere.
  Neither DB-3.zip, DB-4.zip, nor the core's own sql/base/ contains a
  CREATE-TABLE schema for the hotfixes database. HotfixDatabase.cpp
  shows this core expects a large DB2-mirroring schema (achievement,
  achievement_locale, animation_data, adventure_journal, ... one table
  per client DB2 file) — hundreds of tables that must match the
  prepared statements in HotfixDatabase.cpp exactly. The only hotfixes
  file provided (2022_02_02_hotfixes_fix_fishing_spell.sql) is an UPDATE
  that assumes this schema already exists (it does DELETE/INSERT into
  hotfix_data and spell_effect). I have NOT fabricated this schema —
  guessing at hundreds of table definitions that must byte-match C++
  prepared statements is too high-risk to invent. You'll need the
  matching hotfixes base SQL from wherever you sourced DB-3/DB-4 (it's
  normally a separate "hotfixes" or "db_hotfixes" dump), or it can be
  generated by running this core's DB2 hotfix-extractor tool against
  your client's DB2 files if one is included in this build.
  The hotfixes UPDATE file is included standalone (07_hotfixes_UPDATE_ONLY
  — apply manually once you have the base schema).
