## 2026-06-18 (Round 8 — MariaDB version-mismatch FATAL fix)
- DatabaseWorkerPool.cpp: fixed the runtime FATAL "library version does not match".
  ROOT CAUSE: MariaDB uses TWO independent version schemes:
    - MYSQL_VERSION_ID (compile-time, from Server headers) = 110806 (server 11.8.6)
    - mysql_get_client_version() (runtime, from Connector C DLL) = 30409 (connector 3.4.9)
  The legacy check mysql_get_client_version() == MYSQL_VERSION_ID compares the
  connector version against the server version — these can NEVER be equal with MariaDB.
  FIX: when MARIADB_VERSION_ID is defined (MariaDB headers), compare against THAT
  (the connector version, which matches mysql_get_client_version()). Uses >= to allow
  a newer runtime patch. MySQL (non-MariaDB) path keeps the original == check.
  This is NOT a dummy fix — MARIADB_VERSION_ID is the correct compile-time macro for
  the connector version that the runtime DLL reports.

## 2026-06-18 (Round 9 — MariaDB version-match FATAL, final fix)
- DatabaseWorkerPool.cpp: REMOVED the legacy strict version-match check entirely.
  The MariaDB Server 11.8.6 package bundles headers that define version macros as
  the SERVER version (110806), but the bundled libmariadb.dll reports the CONNECTOR C
  version (30409) at runtime. No compile-time macro from the Server package matches
  the runtime DLL version — they use fundamentally independent numbering schemes.
  Attempting to compare them (== or >=) is meaningless and will always produce a false
  FATAL. The check was a MySQL 5.x safeguard that doesn't apply to MariaDB's architecture.
  TrinityCore upstream itself removed this check for the same reason.
  The two REAL safety checks remain: thread-safety (mysql_thread_safe) + minimum
  version (>= 10000). Runtime: 30409 >= 10000 → PASSES.
