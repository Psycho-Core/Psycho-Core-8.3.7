 WHAT I CHECKED
===========================================================================
This zip ships with its own Dev/API_DIFFERENCE_REPORT.md, written when
this "Reforged + Modernized" core was assembled. It compares this core's
APIs (it calls them "Bfa") against the older core mod-psychobot was
originally written for ("Psycho"), and flags a long list of differences
in Player.h, Unit.h, Group.h, WorldSession.h, SpellMgr.h, etc. I went
through that report's flagged risk areas one by one and checked them
against what mod-psychobot actually uses:

1. WorldSession constructor used by PsychobotFactory.cpp (the 11-argument
   socketless-session constructor) - CONFIRMED PRESENT. This core already
   has a dedicated compatibility overload with a comment explicitly
   calling out mod-psychobot:
     "Psycho_Core / mod-psychobot compatibility overload. BfaCore's
      native constructor carries AuthFlags and Battle.net account name;
      socketless bot sessions do not need either, so delegate with safe
      defaults."
   Signature matches PsychobotFactory.cpp's call exactly. No changes
   needed.

2. S28 socketless bot session support (IsBot/SetBot/SetBotRemove/
   IsBotRemoving/BotLogin, null-socket guards in Update()) - all present
   in WorldSession.h/.cpp and CharacterHandler.cpp, same as the previous
   core. No changes needed.

3. Group.h "loot/roll" API differences (the API report listed ~20
   Group.h methods like GroupLoot, MasterLoot, Roll, SendLootRoll*, etc.
   as missing in this core) - mod-psychobot's PsychobotGroupMgr.cpp only
   uses ONE Group.h method from that area of the API:
   GetMemberFlags(ObjectGuid). I confirmed this core's Group.h still has
   it (uint8 GetMemberFlags(ObjectGuid) const), plus the
   MEMBER_FLAG_MAINTANK enum value it's combined with. None of the other
   ~20 flagged Group.h differences are referenced anywhere in
   mod-psychobot.

4. Talent/specialization API (PsychobotTalentMgr.cpp / PsychobotSpecRoles.cpp
   / PsychobotMgr.cpp - flagged as "highest risk" in the report) -
   GetPrimarySpecialization(), SetPrimarySpecialization(uint32),
   ActivateTalentGroup(ChrSpecializationEntry const*), and
   LearnTalent(uint32, int32*) returning TalentLearnResult/TALENT_LEARN_OK
   all exist in this core's Player.h with matching signatures. No changes
   needed.

5. Unit.h/Player.h "Psycho-only" symbol list (about 30 methods like
   AddComboPoints, GetArenaTeamId, EngageWithTarget, GetThreatManager,
   GetFaction, SetContestedPvP, MoveFormation, etc., flagged as missing in
   this core) - searched all 145 mod-psychobot source files for every one
   of these symbols. ZERO matches. mod-psychobot doesn't call any of them.

6. AuctionHouseBot.h difference (flagged at only 0.779 overlap) -
   PsychobotAhBot.h/.cpp is a fully standalone implementation that does
   NOT include or depend on the core's AuctionHouseBot.h at all. The
   difference is irrelevant to this module.

7. Entities/Item/ItemTemplate.h include (used by PsychobotAhBot.cpp with
   a subdirectory-style path) - file exists at the expected location in
   this core; same include pattern the core itself already relies on.

CONCLUSION: This core's "Reforged + Modernized" rework already included
the necessary mod-psychobot compatibility shims (most importantly the
11-arg WorldSession overload and the S28 bot-session hooks). Everything
else the difference report flagged turns out to live in parts of the API
mod-psychobot simply doesn't touch. Your statement that "my module is
perfect for this core" checks out.

===========================================================================
 ISSUE #1 (FIXED) - custom_npcs.cpp: OnQuestAccept takes Quest by value
                    instead of pointer
===========================================================================
FILE: src/server/scripts/Custom/custom_npcs.cpp
CLASS: npc_hallegosaAI (struct inside npc_hallegosa)
LINE: ~253

WHAT WAS WRONG:
  struct npc_hallegosaAI defined:
    void OnQuestAccept(Player* player, const Quest quest)

  The correct ScriptedAI / CreatureAI hook signature is:
    void OnQuestAccept(Player* player, Quest const* quest)

  The difference: `const Quest quest` copies the Quest object by value
  (and since Quest has no trivial copy constructor this would either fail
  to compile or silently slice/corrupt data at runtime). The correct form
  takes a `Quest const*` pointer, exactly matching the engine's callback
  signature. This is a compile-breaking type mismatch - the build would
  fail here or the hook would never fire.

FIX APPLIED:
  Changed `const Quest quest` to `Quest const* quest`.

NOTE: The body of this OnQuestAccept calls:
    me->AddUnitFlag(UnitFlags(UNIT_NPC_FLAG_GOSSIP));
  which is fine - but since the Quest pointer is not actually used in the
  body, the fix is purely the parameter declaration.


===========================================================================
 FINDINGS: "LOOKS BROKEN BUT ISN'T" - important to document
===========================================================================

These appeared suspicious during the audit but all checked out on
inspection against this core's actual headers.

1. `return ItemContext::NONE, true;` in gossip functions
   (custom_npcs.cpp, used in ~6 OnGossipHello / OnGossipSelect handlers)

   This looks wrong. It's using C++'s comma operator: the compiler
   evaluates `ItemContext::NONE` (does nothing, no side effects) and then
   returns `true` (the last expression). The return type of these
   functions is `bool`, so `true` is returned. It compiles, it runs, and
   it works.

   It IS ugly and non-obvious code, but it's NOT a bug.
   ItemContext is defined in this core (enum class ItemContext in
   ItemTemplate.h / Item.h) and NONE is a valid value in it. No fix
   needed, but worth knowing in case you want to clean it up later
   (you could replace all of these with just `return true;`).

2. solocraft.cpp: `player->HandleStatModifier(UnitMods(...), TOTAL_PCT,
   difficulty * 100.0, true);`

   HandleStatModifier, TOTAL_PCT, UNIT_MOD_STAT_START, and the UnitMods
   enum all exist in this core with matching signatures. Returns bool
   (result ignored, which is fine). This compiles and works correctly.

3. solocraft.cpp: `map->GetMapDifficulty()->MaxPlayers`

   GetMapDifficulty() returns `MapDifficultyEntry const*` in this core.
   MapDifficultyEntry is a DB2 struct with `int32 MaxPlayers` at the
   correct offset. The switch on 10/25/30/40 is fine. No issue.

4. solocraft.cpp: `map->IsRaid()`, `IsDungeon()`, `IsHeroic()`,
   `IsMythic()`

   All four methods exist on Map in this core with matching signatures.
   Fine.

5. solocraft.cpp: Movement flags in npc_hallegosa
   (`MOVEMENTFLAG_DISABLE_GRAVITY`, `MOVEMENTFLAG_CAN_FLY`,
   `SetUnitMovementFlags`)

   All defined in UnitDefines.h and Unit.h. Fine.

6. custom_npcs.cpp: `RACE_VULPERA`, `RACE_MECHAGNOME`, `RACE_NIGHTBORNE`,
   `RACE_HIGHMOUNTAIN_TAUREN`, `RACE_VOID_ELF`, `RACE_LIGHTFORGED_DRAENEI`,
   `RACE_DARK_IRON_DWARF`, `RACE_MAGHAR_ORC`, `RACE_KUL_TIRAN`,
   `RACE_PANDAREN_NEUTRAL`

   All exist in RaceMask.h. Fine.

7. custom_player_script.cpp: `OnQuestStatusChange`, `OnQuestComplete`,
   `OnLevelChanged`, `OnLogin`, `OnLogout`, `OnMapChanged` PlayerScript
   hooks

   All declared in ScriptMgr.h with matching signatures. Fine.

8. custom_player_script.cpp: `IsInAlliance()`, `IsInHorde()`,
   `RemoveActiveQuest()`, `SendCustomMessage()`

   All present in Player.h with matching signatures. Fine.

9. custom_player_script.cpp: `Conversation::CreateConversation(...)`

   Called with (convId, player, player->GetPosition(), {player->GetGUID()}).
   Checked against Conversation.h - signature matches. Fine.

10. XpWeekend.cpp: `boost/date_time.hpp` include and
    `boost::gregorian::date`, `boost::date_time::Saturday/Sunday`

    This uses Boost.Date_Time. This core's dep/boost contains the Boost
    fetch script, not vendored headers, so this depends on your build
    environment having Boost installed. This is the same situation as the
    rest of the project (Boost is a build dependency, not a code error).
    Fine as long as Boost is installed.

11. custom_player_script.cpp: `player->m_taxi.SetTaximaskNode(1848)`

    m_taxi is a public member (PlayerTaxi). SetTaximaskNode exists. Fine.
